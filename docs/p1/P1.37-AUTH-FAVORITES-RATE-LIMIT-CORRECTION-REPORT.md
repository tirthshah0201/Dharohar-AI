# P1.37 Authentication, Favorites & Rate-Limit Correction Report

## 1. Executive Summary

Two user-reported runtime bugs were investigated, root-caused, and fixed:

1. **BUG-001**: Authenticated user treated as unauthenticated in Favorites
2. **BUG-002**: Login rate limit blocks registration

**Status: PASS**

## 2. Root Cause Analysis

### BUG-001 — Auth State Lost in Favorites

**Root Cause**: `useFavorites` hook had its own independent auth check via `/api/proxy/auth/me`. This independent check could fail or desync from the main `useAuth` context, causing the Favorites page to show "sign in" even when the user was authenticated through `useAuth`.

**Fix**: Modified `useFavorites` to accept shared auth state (`authenticated`, `isAuthLoading`) from `useAuth` instead of making its own independent auth check. Updated Favorites page to pass auth state from `useAuth`.

### BUG-002 — Login Rate Limit Blocks Registration

**Root Cause**: Line 57 of `backend/src/index.ts` applied a global `authRateLimit` (10 req/15min) to ALL `/api/auth/*` routes:
```javascript
app.use("/api/auth", authRateLimit, authRouter);
```
This meant failed login attempts consumed the shared auth bucket, which also applied to registration. After 5 failed logins, the global auth bucket was at 5/10, and combined with route-specific limits, registration was blocked.

**Fix**: Removed the global `authRateLimit` from the auth router. Route-specific limiters (`loginRateLimit`: 5/15min, `registerRateLimit`: 3/hour) already provide adequate independent protection.
