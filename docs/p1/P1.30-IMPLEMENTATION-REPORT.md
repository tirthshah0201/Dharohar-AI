## Executive Summary

P1.30 upgrades Astrova's browser-only localStorage Favorites system into a persistent, user-based Favorites system backed by Neon PostgreSQL. Users can now register, log in, and have their favorites persist across devices and sessions. The implementation adds JWT-based authentication with HttpOnly cookies, server-side favorites management, and seamless migration from localStorage.

## Database Changes

### Migration: `027_p1_user_auth_persistent_favorites.sql`

**New tables:**

| Table | Purpose |
|-------|---------|
| `users` | User accounts with email/password authentication |
| `user_favorites` | Persistent favorites linked to authenticated users |

**Schema:**

```sql
users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
)

user_favorites (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  heritage_entity_id UUID NOT NULL REFERENCES heritage_entities(id) ON DELETE CASCADE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  UNIQUE(user_id, heritage_entity_id)
)
```

**Indexes:**
- `idx_users_email` — Fast email lookup for login
- `idx_user_favorites_user` — Fast user favorites listing
- `idx_user_favorites_entity` — Fast entity-level queries

**Constraints:**
- UNIQUE on `(user_id, heritage_entity_id)` — Prevents duplicate favorites
- ON DELETE CASCADE for both FKs — Cleanup on user/entity deletion

## Authentication Architecture

### Mechanism
- **JWT** tokens signed with `JWT_SECRET` environment variable
- **HttpOnly cookies** (`astrova_session`) for session transport
- **bcrypt** password hashing (10 salt rounds)
- 7-day token expiration

### Security Features
- Passwords never returned in API responses
- HttpOnly cookie prevents XSS token theft
- Secure flag in production
- SameSite=Lax for CSRF protection
- Server-side session verification on every authenticated request
- User existence verified on each auth check (not just JWT validity)
- Cookie cleared on logout, invalid token, and expired token

### Auth Middleware

| Middleware | Purpose |
|-----------|---------|
| `requireAuth` | Rejects unauthenticated requests (401) |
| `optionalAuth` | Attaches user if available, passes through if not |

### Environment Variables
| Variable | Purpose | Default |
|----------|---------|---------|
| `JWT_SECRET` | Token signing key | `astrova-dev-secret-change-in-production` |
| `JWT_EXPIRY` | Token lifetime | `7d` |

## API Changes

### New Auth Endpoints

| Method | Endpoint | Auth | Purpose |
|--------|----------|------|---------|
| POST | `/api/auth/register` | None | Create account |
| POST | `/api/auth/login` | None | Authenticate |
| POST | `/api/auth/logout` | None | Clear session |
| GET | `/api/auth/me` | Required | Get current user |

### New Favorites Endpoints

| Method | Endpoint | Auth | Purpose |
|--------|----------|------|---------|
| GET | `/api/favorites` | Required | List user's favorites |
| POST | `/api/favorites/:heritageId` | Required | Add favorite |
| DELETE | `/api/favorites/:heritageId` | Required | Remove favorite |
| GET | `/api/favorites/:heritageId/status` | Required | Check favorite status |
| POST | `/api/favorites/sync` | Required | Merge localStorage favorites |

### Validation
- Register: name (≥2 chars), email (valid format), password (≥6 chars)
- Login: email + password required
- Favorites: heritage entity existence verified server-side
- Duplicate favorites prevented at database level

## Favorites Migration Strategy

1. Unauthenticated users store favorites in `localStorage`
2. On login/register, `POST /api/favorites/sync` merges localStorage IDs into PostgreSQL
3. Server uses `ON CONFLICT DO NOTHING` to prevent duplicates
4. After sync, localStorage is updated with the merged server state
5. Post-login, `useFavorites` hook transparently uses backend API
6. If API fails, optimistic UI reverts to previous state

## Known Limitations

1. **Admin auth separate from user auth** — ADMIN_TOKEN is independent of user accounts. This is intentional.
2. **No email verification** — Registration immediately creates an account. Future phase could add email verification.
3. **No password reset** — Not implemented in P1.30. Future feature.
4. **No rate limiting** — Auth endpoints could benefit from rate limiting to prevent brute force. Documented as technical debt.
5. **Test users exist** — `test@astrova.com` and `test2@astrova.com` were created during verification. These can be cleaned up manually.
