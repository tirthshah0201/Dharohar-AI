## 3. Authentication Changes

### JWT Secret Handling
- **Before**: `const JWT_SECRET = process.env.JWT_SECRET || "astrova-dev-secret-change-in-production"`
- **After**: Fail-fast with console error if JWT_SECRET not set. Uses `EFFECTIVE_SECRET` variable.
- **Impact**: Server logs clear warning if JWT_SECRET is missing. No more silent use of weak dev secret.

## 5. Rate Limiting

### Implementation
- **Mechanism**: In-memory sliding window per IP
- **Configurable**: maxRequests, windowMs, keyFn, message
- **Response headers**: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`
- **Cleanup**: Periodic garbage collection every 60 seconds

### Applied Rate Limits

| Endpoint | Limit | Window | Key |
|----------|-------|--------|-----|
| POST /api/auth/register | 3/hour | 60 min | IP |
| POST /api/auth/login | 5/15min | 15 min | IP |
| All /api/auth/* | 10/15min | 15 min | IP |
| All /api/ai/* | 30/min | 60 sec | IP |
| All /api/favorites/* | 30/min | 60 sec | IP |

### Verified
- HTTP 429 returned after limit exceeded ✅
- `Retry-After` header included ✅
- `X-RateLimit-*` headers included ✅
- Normal requests pass through with headers ✅

### Documented Limitation
- Rate limiter is in-memory (single-server only)
- Resets on server restart
- Not distributed/Redis-backed (documented as future improvement for production deployment)

## 6. CORS Configuration

### Before
```js
origin: process.env.NODE_ENV === "production" ? false : true
```
This allowed ALL origins in development with credentials.

### After
```js
origin: process.env.NODE_ENV === "production"
  ? (origin, callback) => {
      if (!origin || ALLOWED_ORIGINS.includes(origin)) {
        callback(null, true);
      } else {
        callback(new Error("Not allowed by CORS"));
      }
    }
  : true
```

- Production: Only allows origins in `ALLOWED_ORIGINS` env var
- Development: Allows all origins (for local dev convenience)
- `credentials: true` maintained for cookie support

## 7. CSRF Protection

### Analysis
- Cookie uses `SameSite: "lax"` — prevents cross-site POST/DELETE requests from including cookies
- All state-changing requests are POST/DELETE which are blocked by SameSite=Lax for cross-origin
- Browser same-origin policy prevents reading responses from other origins
- CORS restricts which origins can make credentialed requests in production

### Conclusion
SameSite=Lax provides adequate CSRF protection for the current Astrova architecture (same-origin frontend ↔ backend via proxy). No additional CSRF tokens needed at this stage.

- Admin APIs cannot be accessed using normal user sessions ✅
- Normal users cannot escalate to admin ✅

### Timing-Safe Comparison
- **Before**: `providedToken !== configuredToken` (vulnerable to timing attacks)
- **After**: `crypto.timingSafeEqual(providedBuf, configuredBuf)` ✅

## 13. Error Handler Security

### Before
```js
console.error("Unhandled error:", err);
res.status(500).json({ success: false, message: "Internal server error" });
```

### After
```js
console.error("[Error]", err.message);
res.status(500).json({
  success: false,
  error: { code: "INTERNAL_ERROR", message: "An unexpected error occurred." }
});
```
- Stack traces never sent to client ✅
- Internal error messages never exposed ✅
- Consistent error response format ✅
